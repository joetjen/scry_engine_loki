# Changelog

## [Unreleased]

### Added

- Initial release: `Scry.Engine.Loki` -- a real `Scry.Core.EngineBehaviour` implementation over Loki, via `req` rather than a dedicated driver (none exists -- Loki's own query API is plain HTTP). The `time-series` kind's *third* real backend, after `scry_engine_ch`/`scry_engine_redistimeseries`, and the first over genuinely non-numeric sample content: a Loki entry's own "value" is a log line (text), not a number. `scry_time_series`'s own `LAST`-lowering pass already rewrites into an ordinary `WHERE` predicate before any engine sees the query -- the identical "zero time-series-specific code needed" finding established three times over now -- so this package's only real work is `Scry.Engine.Loki.RangeQuery`, translating the resulting timestamp-range `WHERE` into LogQL `query_range` bounds.
  **`source` maps onto one Loki label value** (`SELECT myapp { ... }` becomes the stream selector `{job="myapp"}`, `job` configurable), the same "one name maps onto one primary identifier" convention every adapter in this family has. Every row exposes `"timestamp"` (a real `DateTime.t()`) and `"line"` (the raw text, deliberately not named `"value"` since that would misrepresent non-numeric content) plus every real label Loki itself attaches.
  **Extraction, not translation -- a deliberate divergence from `scry_engine_redistimeseries`'s own stricter `RangeQuery`**: since a Loki row has real fields beyond `"timestamp"`/`"line"` (unlike a bare RedisTimeSeries key), this package only ever extracts what it can safely fold into the LogQL request (the required timestamp lower bound, an optional upper bound, any `WHERE <label> = <literal>` equality) and leaves `wheres` untouched for `Scry.Core.QueryOps.run_flat/3` to re-evaluate afterward -- an unrecognized construct is simply not extracted, never an error.
  **An explicit lower time bound is required, not optional**: confirmed directly, Loki enforces a real maximum query time range and silently applies its own default window when `start`/`end` are omitted -- there's no honest default this package could guess, so a query with no extractable `"timestamp"` lower bound declines outright rather than risk silently missing data or a `400`.
  **Two real findings, not assumed**: Loki rejects *out-of-order* pushes to an existing stream, not (only) old-in-absolute-terms ones -- confirmed by re-running the test suite against a long-lived container, fixed by giving every run its own unique `job` label; and Elixir's native `DateTime.t()` is microsecond-precision internally, so a real Loki nanosecond timestamp genuinely loses its last three digits on decode, confirmed directly.
